# ESP32-H2 Bring-up Status

## Goal

Boot an ESP32-H2 arduino "hello" sketch (prints `HELLO_UART_OK` then `TICK` in
a loop) on the rv32emu-based emulator — WASM build, fqbn `esp32:esp32:esp32h2`
— and have it reach `app_main` with UART output.

Status: **NOT converged (WIP).** The H2 model loads the ROM banner and reaches
the app image, but the app's startup spins forever on bootloader-populated
DRAM tables that the emulator leaves zeroed. A stopgap that fills the unloaded
DRAM region with a no-op stub gets past two such tables, then hits a third;
the approach is fundamentally whack-a-mole, so it was shelved (not committed to
`AGENTS.md`, not committed to the tree).

## Environment

- Emulator: `/home/danish1075/Documents/esp-rv32emu` (rv32emu ESP32 port)
- WASM build: emscripten **6.0.6** (3.1.30 breaks the `emruntime-library.js`
  link with `addToLibrary is not defined`). Built with
  `make CC=emcc wasmc6_defconfig && make CC=emcc -j$(nproc)`; the defconfig has
  `CONFIG_ESP32_H2=y` (and `CONFIG_ESP32_C3=y`, `CONFIG_ESP32_C6=y`).
- Firmware: `arduino-cli` (`/home/danish1075/bin/arduino-cli`), esp32 core
  3.3.10, fqbn `esp32:esp32:esp32h2`, built to a `merged.bin` image.
- Headless run: a node wrapper that writes `merged.bin` into MEMFS at
  `/merged.bin`, stubs `document` (the run-button JS library touches it), and

  `Module["noInitialRun"]=true`, so the bare `node rv32emu.js -C ... -F ...`
  CLI does **not** run `main()`.

## What was done (attempt A — populate the tables)

### 1. Reset cause -> POWERON

- Problem: the H2 ROM reported a wrong/unsupported reset cause and boot stalled
  before the banner.
- Fix: in `esp32h2_new()` set `soc->strap_b0410 = 1` so the ROM reports
  `rst:0x1 (POWERON)`. The strap word at `0x600b0410` is produced by the
  reset-cause / `GPIO_STRAP` read path (`src/esp32h2.c:490` set, `:1535` read,
  `:1781` write).

### 2. M-mode override

The ROM is M-mode firmware; early ROM/bootloader code must run in M-mode as on
real silicon. Without this the emulator's default privilege handling broke ROM
execution.

### 3. Removed the 0x4080f280 band-aid

An earlier hack returned `1` on reads of `0x4080f280` to force past a
bootloader-ready spin. Once the real cause (zeroed tables) was understood this
was removed.

### 4. DRAM trampoline/flag fill (stopgap)

In `esp32h2_new()` (`src/esp32h2.c:538-559`): the H2 2nd-stage bootloader and
app reference function-pointer + status-flag tables that live in **unloaded
HP-SRAM** (between the end of the last loaded segment and the top of DRAM). On
real silicon the bootloader writes real target addresses there; the emulator
leaves them `0`.

Stopgap: place a tiny stub at `0x4084FF00`:

```
li  a0, 0      ; 0x00000513
ret            ; 0x00008067  (jalr x0, 0(ra))
```

then fill the entire unloaded region `0x4080d8b8 .. 0x4084FF00` with the stub
address.

Effect: flag slots read non-zero (so spin-wait flag checks pass) and
function-pointer slots jump to the stub, which returns "success" (`a0 = 0`).

## Results of attempt A

- Got past the `0x4080f280` bootloader-ready spin.
- Got past the `esp_timer` startup failure (which was also a zeroed-table check).
- Then hit a 3rd spin at `pc = 0x40809ce6`, which reads a pointer at
  `0x4080EC1C` and calls through it. With the fill that slot holds the stub
  address, so it calls the no-op stub — but the real function it expected would
  have initialized a peripheral. The stub does nothing, so the firmware either
  spins waiting for that peripheral or continues with broken state.
- Conclusion: A is whack-a-mole. Making every zeroed slot a no-op stub "fixes"
  flag spins but breaks the slots that need real behavior, and there are
  multiple such tables (`0x4080f280` flag, `0x4080DDC8` 8-slot fnptr table,
  `0x4080EC1C` via `0x40809ce6`, ...).

## Root cause (hypothesis)

The H2 2nd-stage bootloader is responsible for populating these DRAM
trampoline/flag tables (and the ROM-to-app glue) before jumping to the app
entry. On the emulator these tables remain zero, which means either:

- (a) the H2 bootloader did not actually run / bailed out before its
  table-population step, or
- (b) the bootloader writes to a memory region the emulator does not map for H2
  (e.g. RTC-FAST memory, a DRAM alias, or a region sized differently for H2 vs
  C3/C6), or
- (c) H2 expects a reset/strap/boot-mode path or RTC state the model does not
  reproduce, so it skips the normal bootloader->app handoff that populates the
  tables.

Notably, C3 and C6 boot the same style of arduino sketch with **no** such fill —
so this is H2-specific (likely the H2 ROM/bootloader handoff or a memory-region
difference). The correct fix is to make the real bootloader populate the tables,
not to stub them.

## Possible solutions (in order of preference)

1. **Let the bootloader do its job.** Trace the ROM -> bootloader -> app handoff
   for H2: confirm the bootloader image is present in the `merged.bin` flash
   region and is actually executed; check that the H2 bootloader's
   table-population code runs and writes to a region the emulator maps. Fix
   whatever prevents that (missing region, wrong strap, early bail), rather than
   faking the tables.
2. **If the ROM populates the tables**, verify the H2 ROM image we load
   (`esp32h2_rom_bin`) is the correct revision and that all ROM-visible DRAM/RTC
   regions H2 uses are mapped. A wrong/truncated ROM or a missing RTC-FAST
   region would leave the tables zero.
3. **Load the app ELF directly** (bypass the bootloader) and relocate it in the
   emulator, then synthesize the tables the app needs from what the real
   bootloader would write (read esp-idf / the bootloader source for the exact
   table layout and contents). This is a mini-bootloader in the emulator — more
   correct than the no-op stub, but a reimplementation.
4. **Surgical stub (short term):** only fill the specific *status-flag* slots
   with `1` and leave function-pointer slots pointing at real emulated helpers
   for the few functions the app actually needs (e.g. `esp_timer`,
   `esp_cpu_stall`, cache ops). Still whack-a-mole, but less likely to corrupt
   state than filling everything with one stub.
5. **Diff against C3/C6:** find what H2-specific memory regions / boot flows
   differ (H2 has a different SRAM/LP/RTC layout and boot ROM) and reconcile.

## How to reproduce / debug

- Build: `source ~/emsdk/emsdk_env.sh` (6.0.6); `rm -rf build/softfloat
  build/devices`; `make CC=emcc wasmc6_defconfig`; `make CC=emcc -j$(nproc)`.
- Run headless via the node wrapper (MEMFS write of `merged.bin`, `document`
  stub, `Module.run_system("-C esp32h2 -F /merged.bin")`).
- Watch for `pc` landing in `0x4080xxxx` reading zeroed slots; the `[PCS]` /
  `[DBGPC]` prints show the spin sites. Compare against a working C6 run
  (`-C esp32c6`) to see where H2 diverges.
